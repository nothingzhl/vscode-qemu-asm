# 依赖隔离重构：第一阶段

> 历史阶段记录：以下结果对应文中注明的版本、提交与执行环境，不是当前全部平台的兼容承诺。使用指南见[文档导航](README.md)，当前工具组合见[兼容性](COMPATIBILITY.md)。

本阶段把依赖问题放到实际构建、启动和调试都会经过的边界中处理。保留现有项目配置与 NASM、C 两条调试路径，先交付共享工具解析、宿主进程管理、基础检查、会话能力报告和可选组件降级。逐平台、逐版本适配继续在独立重构分支推进。

## 已接入的边界

| 边界 | 职责 | 实际消费者 |
| --- | --- | --- |
| `src/platform/host.ts` | 扩展执行宿主的系统、CPU、路径语义、环境、进程启动与进程树终止 | 工具解析、`Processes` 与交互式 `MiClient` |
| `src/platform/processes.ts` | 统一解析后用参数数组启动 owned 进程，管理超时、取消和清理 | NASM / 外部构建、QEMU 与基础依赖检查 |
| `src/dependencies/tools.ts` | 将显式入口或 PATH 命令解析为实际启动路径，返回来源、宿主和文件身份 | `Processes` 与 Doctor |
| `src/dependencies/capabilities.ts` | 保存当前会话、目标、工具和机器配置范围内的能力观察 | 两条调试运行时及结构化依赖报告 |
| `src/dependencies/doctor.ts` | 基础检查与报告格式化，复用上述工具与进程边界 | “检查环境”和“查看依赖报告”命令 |

平台层保持窄接口。文件与网络访问继续使用现有 Node API，不新增一套通用文件系统框架。NASM 的 listing、指令步进、BP/EBP 调用链与 C 的 DWARF、GDB 源码步进、栈展开继续分别实现。C 会话通过原有 GDB/MI 通道观察机器，不额外连接第二个 RSP 客户端争用 QEMU。

GDB 的 `MiClient` 持有双向交互流，直接复用统一工具解析和宿主进程树终止；只对自身创建的私有进程组做树清理，公开构造器传入的外部进程保持原有单进程终止语义。

## 解析一个工具，检查和实际执行使用同一规则

`resolveProject` 保留项目级和工作区级配置的原有优先级，并先把配置中的相对路径按所属工作区或项目解析。随后，Doctor 和真正启动进程的 `Processes` 都调用 `resolveExecutable`：

- 显式路径按当前执行宿主的路径语义解析，支持带空格的入口；参数单独作为数组传入。
- 裸命令查当前扩展宿主的 PATH。不会替换用户工具、修改 PATH 或联网安装工具。
- 报告包含原配置、最终启动路径、PATH / 显式配置来源、实际宿主、可获取的规范路径和文件身份。实际启动保留符号链接入口。
- 工具缺失、没有执行权限、路径属于其他平台、需要显式解释器的入口均返回明确原因。

扩展运行在 WSL、Dev Container 或远程宿主时，报告的是该扩展宿主；VS Code 窗口所在系统与 i386 客体不参与猜测工具路径。Windows 的路径规则与原生执行结果需要分别验收，路径规则的单元测试不能代替原生运行。

## 基础检查怎样使用

命令面板中的 `QEMU Assembly: 检查环境`（`qemuAsm.checkEnvironment`）输出中文检查结果。`QEMU Assembly: 打开依赖与能力报告`（`qemuAsm.showDependencyReport`）打开只读 JSON 文档，并返回同一份结构化 Doctor 报告，便于复制和排查问题。

执行检查前仍要求 Workspace Trust。基础检查只做以下操作：

| 项目配置 | 检查内容 |
| --- | --- |
| NASM 构建 | 解析 NASM，并执行 `-v` |
| 外部构建 | 只解析 `build.command`，不运行构建、不自动追加 `--version` |
| 所有项目 | 解析 QEMU，并执行 `--version` |
| 配置 `debug.elf` 的 C 项目 | 解析 GDB，并执行 `--version` |

NASM 调试不要求 GDB，外部构建不额外要求 NASM。C 的编译器和其他项目构建依赖仍由项目管理。工具输出还需要符合 NASM、QEMU 或 GNU GDB 的版本身份；仅打印一个版本数字不会判为通过。非零退出、超时、取消和无法识别的输出均有独立结果，保留的输出长度有上限。

这些检查不构建用户项目、不启动临时客体、不连接已有调试目标，也不会把用户配置的构建命令当作版本查询器。工具版本被识别，只证明本次版本命令执行和身份识别的结果。

## 能力状态与证据分开

`CapabilityLedger` 初始建立以下能力项：`qemu.rspTarget`、`qemu.segmentRegisters`、`qemu.physicalMemory`、`qemu.display`、`gdb.mi`、`decoder`。

每一项同时记录两个维度：

| 维度 | 取值 | 含义 |
| --- | --- | --- |
| 能力状态 | `unknown` / `supported` / `unsupported` | 未得出结论 / 在当前范围内可用 / 在当前范围内不可用 |
| 证据范围 | `not-checked` / `executable` / `protocol` / `integration` | 未检查 / 可执行层面 / 实际协议观察 / 特定组合的集成验收 |

每项还包含原因、观察时间和必要细节；整个报告带会话标识、目标、后端、工具与机器配置范围。实际握手、段寄存器读取、物理内存协议检查等在原有运行时的真实通道上更新观察，不通过工具版本号猜测结果。HMP 的 CR0 与 CS/SS 段缓存关系到模式、地址和栈的正确性；核心输入缺失或无法解释时明确失败，不假定平坦段。

基础 Doctor 不执行协议探针，因此其能力项保持 `unknown` / `not-checked`。缺少可执行文件会体现在工具检查失败中，不会伪造一次协议不支持的结论。若附带活动调试会话的快照，报告会单独保存和显示该会话范围，不把它合并为本次基础检查结果，也不把“协议探针通过”升级为“全部功能集成通过”。

能力账本按会话创建，不进行跨目标永久缓存。重新启动、换工具、换目标或改变机器配置后需要新的账本；快照是独立副本，报告使用者修改 JSON 不会改写运行时记录。

## 可选组件的失败边界

`iced-x86` 仍随 VSIX 提供，但在真正请求解码时延迟加载。缺少模块或 WASM、初始化失败会影响反汇编和依赖解码的操作，不阻止插件加载及基础检查、构建、运行。NASM 在没有源码映射的代码上执行 F10 也需要解码；此时会明确说明受影响操作。C 的源码步进继续由 GDB 执行。

设置 `qemuAsm.displayMode` 支持：

- `auto`（默认）：按原有流程启用模拟显示器；可选显示资源或面板创建失败时记录原因，让构建、运行和基础调试继续。
- `off`：不创建 QMP 显示端口和截图目录，直接使用无显示器流程。

显示资源分配、面板创建、QMP 连接与截图是不同阶段，分别处理失败。取消启动、信任检查失败和核心调试错误不会被当作普通显示问题吞掉。QMP 截图仍要求共享文件命名空间；端口可连接不能证明跨宿主显示可用。以上没有增加远程 attach 或外部 QEMU 所有权管理。

## 平台、版本与验证范围

历史 Linux x64 基线是 NASM 2.16.03、QEMU 10.0.13、GDB 16.3、GCC 14.2，以及 VS Code 1.96.4 / 1.142.0。它们是具体已验版本，**不是根据版本大小自动推定的最低支持版本**。本阶段的实际重跑项目和结果见 [DEPENDENCY_VALIDATION.md](DEPENDENCY_VALIDATION.md)，以其中明确列出的本次验证为准。

基础 Doctor 已在当前 Linux x64 宿主实际识别 NASM 2.16.03、QEMU 10.0.13 和 GDB 16.3，包含带空格的 QEMU / GDB wrapper 路径；所有协议与集成能力仍为未验证。基础检查通过不能替代真实 QEMU、两条调试链、VS Code 宿主和独立安装 VSIX 的验收。

后续按两条轴推进：

1. 先在 Linux 加一个目标发行版自带工具组合，记录每项协议和功能结果；只为已复现的工具差异增加兼容处理。
2. 逐个验收 Windows x64、macOS arm64 的原生进程、路径、超时/取消、进程树清理、显示、NASM/C 调试和安装包。WSL、Dev Container 分别记录，不能代替 Windows 或 macOS 原生结果。

本阶段不以类型检查、路径模拟或版本字符串宣布新的平台 / 工具版本已经兼容。

## 后续工具分发

继续采用轻量 VSIX，优先复用用户已有工具。可选 Tool Bundle、离线工具目录导入、校验和与来源记录属于后续阶段；尚未提供便携包导入器或下载器。不会为了依赖治理默认联网安装、提权、强制 Docker、替换项目构建链或修改用户 PATH。
